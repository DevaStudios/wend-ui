# Update Component Schema

## Overview

`packages/component-schemas` is schema-first: `schemas/components/<tag>.schema.json` is the spec, not a byproduct of finished code (see `packages/component-schemas/README.md`). Once a schema changes — most commonly a new `variant` enum value plus new `x-wend-tokens` entries — six other things need to catch up, and nothing but this checklist ties them together.

## When to use

- Just edited (or about to edit) `packages/component-schemas/schemas/components/*.schema.json`: added/removed a property, an enum value, or an `x-wend-tokens` entry.

## Order, and why

**Schema → tokens → build/validate → CSS → Stencil component → Storybook → rebuild → Figma → docs.**

Tokens come right after the schema, before any code, because CSS and the Stencil component both need to reference *real* token/custom-property names — writing them first means guessing names you'll have to go back and fix once the tokens exist. The component-schemas build step cross-validates `x-wend-tokens` against `packages/tokens/tokens/component/*.json` and fails loudly on an unresolved name — running it right after the token edit catches typos before they propagate into CSS/Stencil/Storybook/Figma, all of which would otherwise silently inherit the same wrong name.

## Steps

1. **Schema.** Finalize `x-wend-tokens` (dot-path, must exactly match a key you're about to add under `packages/tokens/tokens/component/*.json` — no typos) and any `properties`/`enum` changes. If an enum value has no corresponding tokens (e.g. a new variant with nothing in `x-wend-tokens`), that's a gap — ask the user whether to add matching tokens or drop the value, don't guess silently.

2. **Tokens.** Add/update `packages/tokens/tokens/semantic/color.json` (+ `color.dark.json` for anything mode-sensitive) and `packages/tokens/tokens/component/<name>.json`, following the three-tier aliasing convention in `packages/tokens/README.md` (component → semantic → global, not straight to a raw hex). If no design direction was given for a color, pick a reasonable one consistent with neighboring tokens (e.g. reuse the existing danger/feedback ramp for a destructive variant) and say what you picked — don't block on it unless the choice is genuinely ambiguous.

3. **Build + validate.**
   - `npm run build -w packages/tokens` — runs the color-taxonomy validator first, then Style Dictionary.
   - `npm run build -w packages/component-schemas` — cross-validates every `x-wend-tokens` entry against the token source; fails with the exact unresolved name if something doesn't match. Fix here before writing any code that consumes the name.

4. **CSS.** `packages/styles/src/components/<tag>.css` — add the variant rules using the new custom properties. This is the *only* real component-CSS source; never create or edit `packages/web-components/styles/` (looks like a duplicate, isn't — see `sync-tokens-to-figma`'s "Common mistakes").

5. **Stencil component.** `packages/web-components/src/components/<tag>/<tag>.tsx` — extend the variant type/enum and class-name mapping to satisfy the schema's `properties`. Don't hand-edit `src/components/<tag>/readme.md` — it's regenerated by the `docs-readme` Stencil output target on build.

6. **Storybook — both packages.** `packages/web-components/stories/<tag>.stories.tsx` — add args/controls for the new variant value(s) so they're browsable. Then mirror the same args/controls/stories into `packages/react/stories/<tag>.stories.tsx` (React prop names are camelCase — e.g. `iconLeft`/`iconRight` — vs. the web-components story's kebab-case attributes like `icon-left`/`icon-right`; see `packages/web-components/src/components.d.ts`'s `<Tag>Attributes` interface for the exact camelCase names). The two story files are hand-authored and never generated from each other, so a prop/variant/story added to one does not propagate to the other — treat them as two files to update, not one.

7. **Rebuild web-components.** `npm run build -w packages/web-components`. This regenerates the Stencil docs (`docs-readme`, `dist/docs.json`), the React output target, and copies `packages/web-components/src/*.html` + `src/docs/**/*.html` + `src/global/docs.css` into `packages/web-components/www/` (gitignored build output — the `www` output target's `copy` config, which copies the whole `docs/` directory tree recursively, is what does this). If verifying visually, reload the `www/` copy; never hand-edit anything under `www/` directly, it gets silently overwritten on the next build.

8. **Figma.** Push the new tokens as Variables first (follow `sync-tokens-to-figma`), then add the new component variants to the Figma component (`figma-generate-library`/`figma-use` skills — load `figma-use` before any `use_figma` call).

9. **Docs.** Each component has its own page under `packages/web-components/src/docs/components/<component>.html` (**not** the `www/` copy — that's generated, see step 7; and **not** `packages/web-components/src/components/` — that's Stencil's own `.tsx` source tree, a different directory with a confusingly similar name) — add the new variant(s) to the Examples section and update the Props table's `variant` type union to match the schema's enum. A brand-new component (not just a new variant on an existing one) also needs a new entry in the right-hand nav list on *every* `src/docs/components/*.html` page (the `<nav class="wend-sidebar">` block near the bottom of each file) — nothing auto-generates that list.

## Common mistakes

- Editing `packages/web-components/www/*.html` instead of `packages/web-components/src/docs/components/*.html`. `www/` is entirely gitignored generated output (Stencil's `www` output target copies+minifies the `src/` files on build); an edit there is invisible in git and gets clobbered by the next build. The `src/docs/components/*.html` files are the real, tracked doc source — one file per component (as of the 2026-09-09 top-nav-sections/right-nav redesign; `components.html` is now just a redirect stub to `docs/components/button.html`, not the docs source).
- Skipping step 9 entirely. The schema/tokens/CSS/component/Storybook/Figma chain has validation or visual feedback at every step; the hand-authored docs page doesn't — nothing fails if you forget it, so it has to be a deliberate checklist item, not something you'll notice is missing.
- Confusing `packages/web-components/src/docs/components/` (per-component doc *pages*, HTML) with `packages/web-components/src/components/` (Stencil *component source*, `.tsx`/`.css`) — similar names, adjacent directories, completely different purposes.
- Forgetting that the right-nav list on a `docs/**/*.html` page only shows the pages of its OWN section (Components/Foundations/Get Started each have their own flat list — see `global/docs.css`'s `.wend-sidebar*` classes and the top-nav's `.wend-nav__section-link`). A brand-new component page needs the 11-ish-item Components list updated on every existing Components page, not the top nav (which only has the 4 section tabs: Get Started/Components/Foundations/Agent Log, and doesn't change per new component).
- Recreating `packages/web-components/styles/`. It's an untracked, unused duplicate of `packages/styles/src/components/*.css` — `wend-button.tsx`'s `styleUrl` never resolves to it. If you see it, delete it; don't populate it.
- Adding an enum value to a schema without adding matching `x-wend-tokens` entries (or vice versa) — run the component-schemas build (step 3) to catch this before it reaches CSS/Stencil/Figma; don't rely on eyeballing the diff.
- Updating `packages/web-components/stories/<tag>.stories.tsx` but not `packages/react/stories/<tag>.stories.tsx` (or vice versa). The React wrapper's props are auto-generated from the Stencil component and will already work — nothing errors if the React story just doesn't showcase them, so this drift is silent and only surfaces when someone notices a prop "doesn't exist" in one Storybook section but not the other.
