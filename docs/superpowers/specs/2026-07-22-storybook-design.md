# Storybook — design

## Purpose

Add a Storybook implementation covering both `@wend-ui/web-components` and `@wend-ui/react`, resolving to a single Storybook view when run from the project root. This is a dev/QA tool today but must also be deployable as a client-facing static site (per the roadmap's eventual hosted-docs direction), so the design accounts for a build/publish story from the start, not just local dev.

## Goals

- One Storybook instance, one URL, one static build — not a composed set of separately-hosted Storybooks.
- Stories exist for both packages' primary usage pattern: the raw custom element (`<wend-button>`) and the React wrapper (`<WendButton>`).
- Deployable alongside the existing docs site without needing new hosting infrastructure.
- Automated accessibility checks and autodocs where the underlying component metadata supports it.

## Non-goals

- Composing multiple independently-hosted Storybook instances (rejected — see "Architecture" below).
- Wiring Stencil's own dev-server watch mode into Storybook's dev server. Seeing component-source changes in Storybook requires rebuilding `packages/web-components`/`packages/react` first, same as the existing docs site (`components.html`) already requires today. Not a new limitation introduced by this work.
- Interaction/visual-regression testing addons (e.g. `addon-interactions`, Chromatic) — out of scope unless requested later.
- Deriving `argTypes` for web-components stories from the `list_components` MCP tool automatically — hand-authored for now given the small prop surface (see "Story content" below).

## Architecture

**Decision: single unified Storybook instance, `@storybook/react-vite` as the sole framework.**

Rejected alternative: Storybook Composition (a fully-native Storybook per package — `web-components-vite` for `web-components`, `react-vite` for `react` — composed via `refs` in a third root config). This is the more "idiomatic per-framework" option and was seriously considered, but for a *deployable* artifact it means building, hosting, and keeping three separate static outputs in sync, with the root view being an iframe switcher across separately-hosted URLs. That's meaningfully more CI/deploy surface and a source of staleness/CORS failures for what's supposed to be a single client-facing artifact. Rejected in favor of the simpler unified option.

The unified approach works because React can render a raw custom element directly as a JSX intrinsic tag (`<wend-button>`) — so one React-rendered Storybook instance can host stories for both the framework-agnostic web-components API and the React wrapper API, with one config, one dev server, one static build.

## File layout

```
.storybook/
  main.ts        # stories glob: packages/*/stories/**/*.stories.tsx
  preview.ts     # side-effect import of @wend-ui/web-components (registers custom elements)
                 # + import of @wend-ui/styles/dist/index.css (token/component CSS variables)
packages/
  web-components/
    stories/
      wend-button.stories.tsx   # raw <wend-button> usage
  react/
    stories/
      wend-button.stories.tsx   # <WendButton> wrapper usage
```

Stories live in a `stories/` directory **sibling to `src/`** in each package, not inside it. Stencil's own build walks everything under `packages/web-components/src/` and compiles it with its own JSX pragma (`h()`); a `.stories.tsx` file using React's JSX runtime placed inside that tree would risk conflicting with Stencil's compilation. A sibling directory avoids coupling Storybook's build to Stencil's entirely.

`packages/react/src/` is auto-generated by Stencil's React output target on every `web-components` build (`components.ts`, `wend-button.ts`) — another reason stories for that package also live in a sibling `stories/` directory rather than `src/`, so they're never at risk of being touched by the generator.

## Story content & docgen strategy

**`packages/web-components/stories/wend-button.stories.tsx`** — renders the raw custom element directly, with hand-written `argTypes`:

```tsx
const meta: Meta = {
  title: 'Web Components/Button',
  render: (args) => (
    <wend-button variant={args.variant} disabled={args.disabled}>{args.label}</wend-button>
  ),
  argTypes: {
    variant: { control: 'select', options: ['primary', 'secondary'] },
    disabled: { control: 'boolean' },
    label: { control: 'text' },
  },
};
```

`argTypes` are hand-authored (mirroring `component/button.json` and the props table already on `components.html`) rather than derived from Stencil's `docs.json`, since a raw custom element has no TS component for `react-docgen-typescript` to introspect. If more components are added with larger prop surfaces later, revisit sourcing this from the `list_components` MCP tool instead of duplicating by hand.

**`packages/react/stories/wend-button.stories.tsx`** — renders the real wrapper component and gets automatic docgen:

```tsx
import { WendButton } from '../src';
const meta: Meta<typeof WendButton> = {
  title: 'React/Button',
  component: WendButton,
};
```

`@wend-ui/react`'s generated `wend-button.ts` carries real TS prop types with the source JSDoc comments (`/** Disables the button. */`), which `react-docgen-typescript` (via the docs addon) picks up automatically for the controls table and autodocs page — no manual `argTypes` needed here.

Each stories file gets one story per existing example — Default, Secondary, Disabled — matching what's already on the docs site. This does **not** reproduce the Hover/Active static-swatch trick added to `components.html`; that workaround exists specifically because that page is static HTML. Storybook's controls panel already lets you interact with the real component live, so real `:hover`/`:active` states are simply demonstrated by using the rendered story, not a separate swatch.

## Global setup (`preview.ts`)

- Side-effect import of `@wend-ui/web-components` so `<wend-button>` is defined as a custom element before any story renders (equivalent to the existing docs site's `<script type="module" src="build/wend-ui-web-components.esm.js">`).
- Import of `@wend-ui/styles/dist/index.css` so component CSS variables (`--color-button-primary-background-default`, etc.) resolve, matching how `packages/web-components/src/global/global.css` already imports the same file.
- The Funnel Sans Google Fonts `<link>` tags from `packages/web-components/src/index.html` (preconnect + stylesheet), added via Storybook's `main.ts` `staticDirs`/head-injection mechanism, so `font-family-base` actually renders as Funnel Sans instead of falling back to the generic sans-serif in the token's fallback chain.

## Addons

- Whatever ships as core in the current Storybook major (controls, docs, actions are bundled by default in modern Storybook releases — confirm exact package shape against the installed version at implementation time rather than pinning here).
- `@storybook/addon-a11y` for automated accessibility checks per story.

No interaction-testing or visual-regression addons at this time (see Non-goals).

## Scripts

Root `package.json` gains:

- `storybook`: `npm run build -w packages/web-components && npm run build -w packages/react && storybook dev -p 6006`
- `build-storybook`: same build prerequisites, then `storybook build`

The build-first step is required because Storybook needs the compiled custom-elements bundle and the compiled React wrapper to import — it does not compile Stencil/React-output-target sources itself.

## CI / deployment

Extend the existing [deploy-docs.yml](../../../.github/workflows/deploy-docs.yml) workflow rather than adding a new one — GitHub Pages serves one site per repo by default, and that workflow already owns the Pages deploy for the docs site.

```yaml
- run: npm run build -w packages/react
- run: npm run build-storybook -- -o packages/web-components/www/storybook

- uses: actions/upload-pages-artifact@v3
  with:
    path: packages/web-components/www
```

Storybook's static output is built directly into a `storybook/` subfolder of the `www` directory that's already uploaded as the Pages artifact. The docs site stays at the Pages root; Storybook lands at `<pages-url>/storybook/`. One deploy, one artifact, no new hosting target. Storybook's `build-storybook` will need its output configured for subpath-relative asset resolution (Vite `base`/Storybook's manager-base equivalent) — the implementation plan pins down the exact config option against the installed Storybook version.

## Verification plan

- `npm run storybook` from repo root → confirm both `Web Components/Button` and `React/Button` sections appear in the sidebar, controls work, and the a11y panel reports no violations on the default story.
- `npm run build-storybook` → confirm static output builds without errors.
- Load both story groups in the Browser pane and confirm the button renders with correct token-driven colors (same check already used for `components.html`).
- After extending `deploy-docs.yml`, confirm (by reading the workflow, not by pushing to `main`) that the artifact structure places Storybook under `/storybook/` without clobbering the existing docs site output.
